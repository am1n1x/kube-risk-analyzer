# `kube-risk-analyzer`

**Инструмент гибридного анализа рисков опасного поведения в кластерах Kubernetes (CSPM / BAS)**

 Программный комплекс предназначен для проактивного обеспечения безопасности контейнерных приложений. Объединяет в себе статический аудит конфигураций (Cloud Security Posture Management) и активную валидацию эксплуатируемости уязвимостей (Breach & Attack Simulation).


## 1. Назначение и ключевые возможности

В отличие от классических статических сканеров, порождающих большое число ложных срабатываний из-за отсутствия контекста выполнения («alert fatigue»), `kube-risk-analyzer` реализует подход **непрерывного управления воздействием угроз (CTEM)** и строит сквозные цепочки атаки (**Critical Chains**).

### Ключевая функциональность комплекса:
*   **Гибридный статический анализ (CSPM):**
    *   **Workload:** проверка конфигураций манифестов подов (`privileged`, `hostNetwork`, `hostPID`, `hostIPC`, запуск от root, отсутствие ограничений Capabilities и др.) на соответствие эталонным профилям CNCF Pod Security Standards.
    *   **RBAC:** анализ ролевой модели разграничения доступа (`Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding`, `ServiceAccount`) с поддержкой wildcard-сопоставлений ресурсов и методов.
    *   **Network:** детектирование избыточной сетевой экспозиции (публикация сервисов `NodePort`, `LoadBalancer` и сопоставление открытых портов баз данных с внешними адресами).
*   **Активная верификация эксплуатируемости (BAS):** выполнение безопасных контролируемых payload-сценариев непосредственно внутри подов через `Kubernetes exec API` (`kubernetes.stream`). Включает 7 базовых симуляций (MITRE ATT&CK for Containers).
*   **Контекстная корреляция рисков (Critical Chains):** автоматическое построение и приоритизация атакующих цепочек. Если уязвимая конфигурация пода пересекается с опасными RBAC-привилегиями его учетной записи (`ServiceAccount`), система регистрирует комбинированный инцидент критического уровня (`CRITICAL CHAIN`).
*   **Проактивный Admission Control:** предотвращение деплоя небезопасных манифестов на этапе обращения к API-серверу посредством интеграции `ValidatingAdmissionWebhook`.
*   **Автоматическое исправление (Auto-Remediation):** алгоритмическая мутация YAML-манифестов для их приведения в соответствие жесткому профилю безопасности *PSS Restricted* (отключение privileged-режимов, сброс capabilities, принудительный запуск не от root).
*   **Автономный событийный мониторинг (Runtime Watcher):** Фоновый поток, подписанный на Watch API Kubernetes, который автоматически сканирует новые поды сразу после их создания (за исключением системных пространств имен).

## 2. Архитектура и технологический стек

Программный комплекс спроектирован для работы в изолированных корпоративных контурах (**Air-Gapped Environments**) с минимальным потреблением аппаратных ресурсов.

*   **Backend:** Python 3.10+, FastAPI (асинхронная обработка запросов, DI через `Depends`), SQLAlchemy 2.0.
*   **Database:** SQLite в режиме WAL (Write-Ahead Logging) для поддержки параллельного конкурентного доступа со стороны API, watcher-потока и бэкап-задач. Миграции схемы управляются через Alembic.
*   **Frontend:** Zero-Build SPA (Single Page Application) без промежуточного этапа сборки. Интерфейс реализован на Alpine.js, Tailwind CSS (в runtime) и DaisyUI. Все зависимости (включая библиотеки визуализации Chart.js и vis-network) сохранены локально в `app/static/`, внешние CDN-вызовы исключены.
*   **Безопасность комплекса (Defense-in-Depth):** 
    *   Терминация взаимного TLS (mTLS) на уровне Nginx для криптографического контроля доступа.
    *   Аутентификация пользовательских сессий с хэшированием паролей по стандарту PBKDF2-HMAC-SHA256 (100 000 итераций) с индивидуальной солью (константное сравнение времени через `hmac.compare_digest`).
    *   Автоматическое резервное копирование SQLite БД по расписанию (раз в 24 часа) с ротацией (хранение последних 10 копий) через транзакционно-безопасный метод `sqlite3.Connection.backup()`.


## 3. Быстрый старт в режиме разработки (Local Dev / Minikube)

### 3.1. Подготовка окружения и Kubernetes

Для локального тестирования рекомендуется использовать локальный кластер `Minikube`.

1. Запустите Minikube (с драйвером docker или виртуальной машиной):
   ```bash
   minikube start --driver=docker
   ```

2. Снимите слепок текущей конфигурации кластера (для проверки режима офлайн-анализа):
   ```bash
   kubectl get role,clusterrole,rolebinding,clusterrolebinding -A -o yaml > cluster_dump.yaml
   # Поместите данный дамп в директорию dumps/ проекта, если планируете тестировать локально
   mkdir -p dumps
   mv cluster_dump.yaml dumps/
   ```

3. (Опционально) Запустите встроенный Dashboard Kubernetes для контроля ресурсов:
   ```bash
   minikube dashboard
   ```

### 3.2. Настройка бэкенда приложения

1. Клонируйте репозиторий и перейдите в его корень:
   ```bash
   git clone https://github.com/am1n1x/test-protocol-system.git
   cd test-protocol-system
   ```

2. Создайте и активируйте виртуальное окружение Python:
   ```bash
   python3 -m venv venv
   source venv/bin/activate
   ```

3. Установите зависимости:
   ```bash
   pip install -r requirements.txt
   ```

4. Примените миграции базы данных через Alembic (база `data/kube_risk.db` будет создана автоматически):
   ```bash
   alembic upgrade head
   ```

5. Запустите веб-сервер Uvicorn в режиме автоперезапуска:
   ```bash
   uvicorn app.main:app --reload
   ```

При первом запуске система автоматически наполнит базу данных 20 встроенными правилами анализа из файла `rules.json`, зарегистрирует дефолтные BAS-скрипты, а также создаст администратора по умолчанию:
*   **Имя пользователя:** `admin`
*   **Пароль:** `KubeRisk2026!`

Приложение будет доступно по адресу: `http://localhost:8000`.

## 4. Развертывание в кластере (Production/K3s)

Для развертывания непосредственно внутри защищаемой инфраструктуры (например, на одноузловом кластере k3s под управлением Ubuntu VPS) используется поставляемый Dockerfile и манифест `k8s-deploy.yaml`.

### 4.1. Сборка и импорт образа без внешнего реестра (Air-Gapped)

1. Соберите образ на сборочном хосте:
   ```bash
   docker build -t kube-risk-analyzer:latest .
   ```

2. Экспортируйте его в tar-архив:
   ```bash
   docker save -o kube-risk-analyzer.tar kube-risk-analyzer:latest
   ```

3. Скопируйте tar-архив и файл манифеста `k8s-deploy.yaml` на целевой VPS:
   ```bash
   scp kube-risk-analyzer.tar k8s-deploy.yaml user@vps_ip:/home/user/
   ```

4. На целевом VPS импортируйте образ в пространство имен рантайма k3s:
   ```bash
   sudo k3s ctr -n k8s.io images import /home/user/kube-risk-analyzer.tar
   ```

### 4.2. Применение манифестов

Примените манифест развертывания в кластере. Он создаст необходимый `ServiceAccount` с правами `cluster-admin` (требуется для глубокого сканирования RBAC и использования Exec API), `Deployment` и `Service` типа `NodePort` (порт 30080):

```bash
kubectl apply -f k8s-deploy.yaml
```

Для обеспечения персистентности базы данных и истории дампов манифест настраивает `hostPath`-монтирования:
*   Файл базы данных и бэкапы: `/var/lib/kube-risk-analyzer/data` -> `/workspace/data`
*   Директория офлайн-дампов: `/var/lib/kube-risk-analyzer/dumps` -> `/workspace/dumps`

## 5. Настройка проактивного Admission Control

Для перехвата попыток создания потенциально опасных конфигураций необходимо зарегистрировать приложение в качестве `ValidatingWebhookConfiguration` в API-сервере Kubernetes.

Для автоматической генерации внутренней PKI (CA и сертификатов сервера с корректным расширением `SubjectAlternativeName` (SAN) под ваш узел кластера), а также для публикации конфигурации вебхука выполните скрипт автонастройки:

```bash
chmod +x setup_admission.sh
./setup_admission.sh
```

Данный скрипт:
1. Создаст локальный CA и выпустит сертификаты для шифрования трафика между API-сервером и вебхуком комплекса.
2. Пропишет закодированный в Base64 сертификат CA (`caBundle`) в манифест `admission-webhook.yaml`.
3. Применит конфигурацию вебхука к вашему кластеру.

С этого момента при любой попытке выполнить `kubectl apply` или `kubectl run` для рабочей нагрузки, нарушающей правила из базы данных (категория `workload`), API-сервер отклонит операцию, а в истории событий `kube-risk-analyzer` появится запись вида `Admission Blocked: ...`.

## 6. Демонстрация работы (Тестирование политик)

### 6.1. Тестирование блокировки проактивной защиты (Admission Block)

Запустите тестовый под, нарушающий политику безопасности (запуск в привилегированном режиме `privileged: true`):

```bash
kubectl run test-privileged --image=nginx --overrides='{"spec":{"containers":[{"name":"nginx","image":"nginx","securityContext":{"privileged":true}}]}}'
```

**Ожидаемый результат:** API-сервер вернет ошибку и заблокирует создание пода, ссылаясь на ответ валидационного вебхука. В веб-интерфейсе комплекса на вкладке "History & Reports" отобразится новая запись о предотвращенной угрозе.

Удаление следов теста (если под не заблокировался по причине выключенного вебхука):
```bash
kubectl delete pod test-privileged --ignore-not-found=true
```

### 6.2. Проведение активных BAS-тестов

1. Перейдите в веб-интерфейс на вкладку **Control Panel**.
2. В секции **Breach & Attack Simulation** выберите пространство имен и запущенный под, в котором хотите произвести валидацию.
3. Выберите тип вектора атаки (например, *Container Socket Escape* или *Token Theft*).
4. Нажмите **Run Simulation**.
5. Программа выполнит инъекциюpayload-кода в под. Результаты тестирования с подробным выводом логов команды (`stdout/stderr`) и картой сопоставления техник по классификации MITRE ATT&CK отобразятся на экране и сохранятся в базе данных.

## 7. Контроль качества кода и DevSecOps пайплайн

Проект поставляется с настроенным трехстадийным конвейером проверки безопасности кода (GitHub Actions `.github/workflows/deploy.yml`):

1.  **Stage 1: Security & Lint** (Блокирующий шаг)
    *   **TruffleHog:** Проверка коммитов на наличие жестко зашитых секретов (пароли, ключи, токены).
    *   **Ruff:** Быстрый линтинг кода на соответствие PEP 8.
    *   **Bandit:** Статический анализ безопасности (SAST) Python-кода (блокировка при уязвимостях класса `Medium+`).
    *   **pip-audit:** Анализ состава сторонних зависимостей (SCA) на основе PyPI Advisory Database.
2.  **Stage 2: Build & Transfer**
    *   Сборка Docker-образа, экспорт в OCI-tarball и передача артефактов на продуктивный хост по защищенному каналу SCP.
3.  **Stage 3: Deploy**
    *   Обновление образа в рантайме k3s на VPS и перезапуск пода со стратегией `Recreate`.
